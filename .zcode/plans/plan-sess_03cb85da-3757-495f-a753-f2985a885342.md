# 无障碍服务可行性验证原型

## 验证目标（真机实测三个问题）
1. 用户在系统「设置 → 辅助功能」启用后，`onConnect` 是否触发、服务是否存活
2. `onAccessibilityEvent` 是否收到事件（`windowUpdate`/`pageContentUpdate` 等）
3. 核心问题：SDK 中已 `@deprecated since 12` 的 `getWindows()` / `getWindowRootElement()` / `attributeValue()` 在 HarmonyOS 6.1.1(24) 运行时**是否仍对三方应用开放**、能否提取到第三方页面文本（还是抛 9300003/9300004）

注：这些 API 在 API 24 SDK 中仍可编译（仅弃用警告），且是三方应用唯一可用的读取路径（新接口为系统应用专用）——原型即实测该路径是否仍放行。无论结果如何都有结论价值。

## 新增文件（3 个）

1. **`entry/src/main/ets/accessibility/AccessibilityExtAbility.ets`** — `extends AccessibilityExtensionAbility`（`@kit.AccessibilityKit`）：
   - `onConnect()`：hilog 记录 + 注册到 Monitor；并立即做一次主动抓取验证
   - `onDisconnect()`：注销
   - `onAccessibilityEvent(event)`：hilog 记录事件类型，转发 Monitor
2. **`entry/src/main/ets/accessibility/AccessibilityMonitor.ets`** — 同进程单例（UIAbility 与 ExtensionAbility 默认同进程）：
   - `bind/unbind`：服务就绪状态 → 写 AppStorage（`a11y_ready`）
   - `onEvent`：对 `pageContentUpdate`/`windowUpdate` 做 1s 防抖 + 3s 节流的**被动自动抓取**（只打 hilog + 存 lastResult，不污染剪贴板）
   - `dumpNow()`（主动路径，气泡按钮触发）：`context.getWindows()` → 过滤自身 bundleName、`isVisible` → 递归 `attributeValue('children')` 遍历（深度≤20、节点≤500），收集 `text`/`contents`/`description` → 结果写 hilog + AppStorage（`a11y_last`）
3. **`entry/src/main/resources/base/profile/accessibility_config.json`** — `{ "accessibilityCapabilities": ["retrieve"] }`

## 验证方式
- 编译：`hvigorw assembleHap --no-daemon`（AGENTS.md 中的命令，需设 `DEVECO_SDK_HOME`）；deprecated API 预期仅警告
- 真机：安装 → 系统设置开启服务 → 打开任意第三方 app（如微信/浏览器）→ 点悬浮球 → 点「识屏」→ 观察 toast/hilog（`CopyBubble/A11y` tag）：
  - 抓到文本 = 可行性成立
  - 9300003/9300004 报错 = HarmonyOS 6.1 三方应用无障碍读取已关闭，原型即为结论
- 说明：模拟器对无障碍支持不全，**建议真机验证**

原型不改变既有产品行为；验证完可按需保留或整体移除。
